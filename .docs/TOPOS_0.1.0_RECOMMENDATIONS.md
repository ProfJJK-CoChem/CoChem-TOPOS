The first priority is a trustworthy, reproducible conformer workflow with explicit scientific limits. Preserve the Base → TOPOS → TORQ architecture, independent conformer searches, conservative deduplication, human review and durable ensemble handoff. Add method, chemical-state, units and evidence contracts before broadening the number of methods or distributed services. The [SRS](CoChem-TOPOS_SRS.md) defines the proposed release requirements; this document explains alternatives, drawbacks and deferred work. It does not assert that an engine integration, benchmark, council release or publication has been completed.

The supplied [method_matrix.md](method_matrix.md) identifies itself as `COCHEM-SPEC-TASK2-4-4-METHOD-MATRIX-MAPPING-2026`, a **scientific-constraint mapping**, rather than the complete purpose × time-budget × CPU/GPU matrix described in the original SRS. The complete matrix remains a source dependency. No missing rows, hardware assignments, method substitutions or completion-time guarantees are invented here. The available recipes and legacy code routes must retain their actual source, revision and validation status.

### Publication flow and academic rigor

The proposed publication flow is: preserve inputs and native outputs → validate typed results and scientific scope → evaluate independent reference cases and sensitivity → seal a versioned ensemble with review history → generate SI/methods and a machine-readable manifest → author review → export or explicitly requested deposition. A missing validation does not require hiding usable exploratory data; it requires a clear exploratory label and limits on claims. Separate methodology papers, validation datasets and application results so evidence for one is not used to imply the others.

Use primary method papers for chemistry claims and pinned official documentation for executable syntax. Cite the actual engine, methods, basis/composite, model artifact, mass/constant database, search algorithm and external dataset used in each result. Historical council documents establish project decisions, not peer-reviewed support for accuracy. Record exact-version software/data citations as well as concept-level identifiers where the repository service supports them. Checksums establish integrity; reproducibility additionally requires a runnable recipe, units, parameterization and accessible dependencies. [S09–S11](TOPOS_0.1.0_REFERENCES.md#s09)

Before a new scientific capability is promoted, predeclare its chemical domain, independent reference set, metric/tolerance, uncertainty model and allowed exclusions. Report failures and coverage of the domain, not only averages over successful examples. Keep model selection/training sets separate from validation sets, and avoid tuning thresholds repeatedly on the release benchmark. For stochastic sampling, report independent seeds and recovered-ensemble variability instead of a universal “complete search” score.

## 4. Disposition of every original improvement proposal

The index below covers **108 of 108** original top-level `> - ` proposals, in original order. `P001`–`P108` are new inventory identifiers, not historical requirement numbers. Original chapter/line references refer to the short SRS at source commit `ce6cd25`; Git retains its full wording. Longer claims are summarized by intent, without adopting unsupported guarantees. The three nested scientific-evaluation/pro/con bullets beneath P058 are retained through R05/E17 and its cost/risk disposition.

Dispositions:

- **Keep:** retain the requirement intent for the 0.1.0 SRS; implementation and acceptance evidence remain necessary.
- **Correct:** retain a scoped/corrected version for 0.1.0; the original mechanism or scientific claim requires the qualification shown.
- **Defer:** preserve as a later option with a benchmark/architecture decision before implementation.
- **Engine-owned:** preserve the research idea for the responsible scientific engine/library, outside TOPOS 0.1.0 implementation scope.
- **Replace:** preserve the scientific goal through the stated safer alternative; do not adopt the original unsupported mechanism.

## 5. Decision record for future implementation

For each deferred, replaced or engine-owned proposal, record an owner, chemical/use-case scope, related R/E/P identifiers, authoritative sources, proposed change, baseline comparator, independent validation metric, expected compute/storage cost, failure/recovery behavior and rollback. Acceptance must describe observable behavior and retained evidence. Promotion into a later release requires a documented decision and versioned SRS update; an item appearing in this register is not approval to implement it.
